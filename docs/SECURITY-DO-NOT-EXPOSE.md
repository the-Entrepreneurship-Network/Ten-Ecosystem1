# What must never be exposed — TEN Portal

This portal holds the personal data of 5,000+ students: names, email addresses,
WhatsApp numbers, colleges, attendance records, uploaded résumés and marksheets,
payment references, and the credentials they use to log in.

This document says what must stay private, what is safe to publish, and the
rules that keep the two apart. It is written to be read by anyone on the team,
not only engineers.

---

## 1. Secrets — environment only, never in the repository

These belong in the deployment environment (EC2 environment variables, or a
secrets manager). They must never appear in a committed file, a chat message, a
screenshot, a support ticket, or a browser.

| Variable | What it protects | If it leaks |
|---|---|---|
| `MONGODB_URI` | The entire database | Full read/write of every student record |
| `SESSION_SECRET` | Login session signing | Anyone can forge a session as any user, including admin |
| `ADMIN_API_SECRET` | Maintenance endpoints | Bulk attendance rewrites, student flag changes |
| `ADMIN_PASSWORD_HASH` | The admin portal | Full control of every account |
| `HR_CREDENTIALS` | All HR logins | Access to every student's records and documents |
| `COORDINATOR_CREDENTIALS` | All coordinator logins | Attendance and approval tampering |
| `SES_SMTP_USER` / `SES_SMTP_PASS` | Outbound email | Phishing sent from your own domain |
| `PAYMENTSETU_API_KEY`, `PAYMENT_WEBHOOK_SECRET` | Payments | Forged payment confirmations |
| `GEMINI_API_KEY` | AI assistant | Billed usage on your account |
| `GITHUB_TOKEN` / `GITHUB_PERSONAL_ACCESS_TOKEN` | Repo writes | Malicious code pushed to your repository |
| `ASSISTANT_ADMIN_TOKEN` | Assistant tier grants | Free paid tiers |

`config/secrets.js` checks these at boot. In production a missing or weak secret
**aborts startup** rather than falling back to a default.

**Rotating a secret is not optional after a leak.** A secret that has ever been
committed, pasted into a chat, or returned by an endpoint must be considered
known forever — git history keeps it even after the file is deleted.

> Note: rotating `SESSION_SECRET` signs everyone out. That is expected. Plan it
> for a quiet hour and tell students they will need to log in again.

## 2. Passwords

**A password must never be stored in a form anyone can read back — including
you.** Only a bcrypt hash is stored. A hash cannot be reversed, so nobody, at
any privilege level, can look up what a student's password is.

That means:

- There is no "reveal my password" feature, and there must never be one again.
  A student who forgets their password uses **Forgot password**, which emails a
  single-use reset link that expires in an hour.
- Support staff must never ask a student for their password, and can never tell
  a student what their password is. If someone claims they can, that is a
  warning sign.
- Passwords must never be written to a log file, a console line, an analytics
  event, or a URL. A password in a URL ends up in browser history, in the
  `Referer` header sent to other sites, and in every server access log.
- Password **hashes** are secrets too. They are not returned by any API.

The same applies to the `HR_CREDENTIALS` / `COORDINATOR_CREDENTIALS` maps: they
hold bcrypt hashes, generated by `scripts/generate-credentials-env.js`. When you
create or rotate an account, run that script and delete the plaintext file it
read from.

## 3. Student personal data

Never publish, and never return to anyone who is not the student themself or
authorised staff:

- Email addresses, WhatsApp/phone numbers, home college in combination with a
  full name
- Uploaded documents — résumés, marksheets, ID proofs (`uploads/documents/`)
- Generated PDFs — offer letters, LOC, LOR, LOP, Star awards
- Attendance history, performance scores, payment records, fines
- The local fallback database (`.data/local_db/`) — it is a complete copy of the
  user table

None of these directories may be committed to git. `.gitignore` covers them;
check it before adding a new upload path.

**Bulk exports are the highest-risk artefact in the product.** A CSV of all
students is a data breach in a single file. Export only what a specific task
needs, delete it when the task is done, and never email one or put one in a
shared drive.

## 4. What *is* safe to make public

The certificate verification page is intentionally public — that is what makes a
TEN certificate checkable by an employer. Given a document number,
`GET /api/verify-document/:id` returns:

- Student name
- Employee ID
- Document type (Offer Letter, LOC, LOR, Star Award)
- Domain
- College
- Issue date
- Issuing organisation

It deliberately does **not** return credentials, email address, phone number,
attendance percentage, marks, or payment status. An unknown document number
returns a clean "not found", never a server error.

This is the correct trade-off: a verifier needs enough to confirm the document
is genuine, and nothing more. Keep it that way — do not add fields to this
response because they were convenient for some other page.

---

## 5. Rules that keep it this way

1. **Secrets come from `process.env`, with no fallback literal.**
   `process.env.X || 'some-default'` turns a secret into a public one, because
   the default ships in the repository. If a secret is missing, fail loudly.

2. **Never send a secret to the browser.** Anything in an HTML file, a
   client-side `.js` file, or an API response is readable by every visitor —
   "hidden" fields and obfuscation included.

3. **Identity comes from the session, never from the request.** A header, query
   parameter or body field naming a user is a *claim by the caller*, not proof.
   Use the guards in `middleware/sessionAuth.js`.

4. **Return an allow-list, not the whole document.** Prefer building the
   response object explicitly. Note that `.select()` is a no-op in the JSON
   fallback engine, so a projection alone is not a safety guarantee — see
   `sanitizeStudent()` in `server.js` for the pattern.

5. **Never log credentials.** Not the password, not a token, not a session id —
   not even the length, which narrows a guess.

6. **Never put sensitive values in a URL.** Use a POST body.

7. **Escape anything a user typed before putting it in a page.** Use
   `textContent`, or escape before `innerHTML`. A student's "contribution" text
   is rendered in the HR portal; unescaped, it runs code in the reviewer's
   session.

8. **New upload directory? Add it to `.gitignore` first.**

---

## 6. If you think something has leaked

1. **Rotate the secret immediately.** Do not wait for confirmation.
2. **Force password resets** for any account whose credentials may be involved.
3. **Check the access logs** for use of the exposed path before you closed it.
4. **Tell whoever owns the data.** For student personal data that may mean a
   disclosure obligation — do not decide that alone.
5. **Assume git history still has it.** Deleting the file is not enough; the
   value must be rotated regardless.

## Appendix — issues found and fixed in the security pass

Recorded so the same shapes are recognisable if they reappear.

| Issue | Where it was |
|---|---|
| Admin login granted access with **any** password for any username containing "admin"/"growth"/"vishal" | `middleware/adminAuth.js` |
| Anonymous remote code execution on the production host | `POST /code/run` |
| Anonymous endpoint returning all HR + coordinator passwords in cleartext | `GET /api/secrets-status` |
| Anonymous endpoint rewriting `.env` and repointing the database | `POST /api/save-secrets` |
| Anonymous endpoint returning any student's cleartext password by employee ID | `POST /get-my-password` |
| Cleartext password stored beside the hash and refreshed on every login | `Student.plainPassword` |
| Client-supplied `x-employee-id` overriding the session (act as any student) | v2 route guards |
| Client-supplied `x-ecosystem-user-role` header granting any role | `middleware/roleGuard.js` |
| `Bearer hr_` / `Bearer ` prefix checks accepted any matching string | HR + task-approval endpoints |
| `Bearer mysecret123` hardcoded in source **and** shipped to the browser | `GET /students`, `public/dashboard.html` |
| Undocumented HR backdoor password, not overridable by config | `/hr-login` |
| Session signing key with a committed fallback value | `SESSION_SECRET` |
| Session cookie `Secure` flag downgraded by a client-controlled header | session middleware |
| Full user table (with password hashes) downloadable over HTTP | `/uploads/local_db/db_Student.json` |
| Unvalidated PR URL stored and rendered raw into the HR portal (stored XSS) | `star-submit` → `hr-portal.html` |
| Login rate limit bypassable by varying an unused field | `loginLimiter` key generator |
| Password hash and reset token returned in the login response | `POST /login` |
| Student password reset stored the new password in cleartext | `POST /auth/reset-password` |

Run `bash scripts/verify-security.sh` against a running server to confirm these
stay closed.
